# Модели оценок (экспериментальная V1)

Документ описывает формулы, пороги, ограничения и происхождение исходных данных
двух метрик приложения **Dota 2 Analytics**:

1. **Match Experience Score** — «Качество матча» (главная метрика сайта);
2. **Player Performance Score** — «Качество вашей игры».

> Это начальные гипотезы, а не научно откалиброванная модель. Результат —
> приблизительная автоматическая оценка, а не объективная истина и не замена
> личному впечатлению игрока. Метрики не сводятся к победе или поражению.

Все веса и пороги вынесены в `src/analytics/config.ts` и настраиваются централизованно.
Все формулы реализованы чистыми функциями без обращения к сети и покрыты тестами
(`src/test/experienceScore.test.ts`, `src/test/playerPerformance.test.ts`).

## Источник данных

- Публичный **OpenDota API** (`https://api.opendota.com/api/`), без API-ключа.
- Запросы: `GET /players/{id}`, `GET /players/{id}/matches?game_mode=23`,
  `GET /matches/{id}`, `GET /constants/{heroes|items|game_mode|lobby_type}`.
- **Происхождение полей**: все показатели берутся из ответа `GET /matches/{id}`
  (игроки, `radiant_gold_adv`, `radiant_xp_adv`, `teamfights`, `objectives`,
  `purchase_log`) и краткой истории (`kills/deaths/assists/gold_per_min/...`).
- Поле `radiant_gold_adv`/`radiant_xp_adv` существует только у матчей,
  обработанных парсером OpenDota. Для необработанных матчей рядов нет.
- Автоматический разбор реплеев (`POST /request/{id}/parse`) **не запускается**,
  чтобы не расходовать квоту API.
- Отсутствующие поля никогда не заменяются нулями: слой `MatchMapper`
  (`src/domain/mappers/matchMapper.ts`) оставляет их `undefined`, а слой оценок
  помечает компонент как «нет данных» и перераспределяет веса.

## 1. Match Experience Score («Качество матча»)

Модель: `src/analytics/experience-score/index.ts`.

### Веса компонентов

| Компонент | Вес | Источник данных |
|---|---:|---|
| Равенство и напряжённость (parity) | 30% | `radiant_gold_adv`, `radiant_xp_adv` |
| Возможность влиять на игру (agency) | 25% | kills/assists, `hero_damage`, `tower_damage`, `hero_healing` |
| Полезность союзников (teamwork) | 25% | ассисты всех игроков команды, `tower_damage`, `hero_healing` |
| Темп и вовлечённость (pace) | 20% | `duration`, kills+deaths, `teamfights` |

### 1.1. Равенство и напряжённость (0–100)

Считается **только по временным рядам**. Если рядов нет — компонент
**недоступен**; равенство не выводится из конечного счёта.

Знак ряда приводится к стороне игрока: `value * sign`, где `sign = +1` для
Radiant и `-1` для Dire.

Составляющие (усредняются с равными долями по доступным):

1. **Доля времени в интриге** (`intrigueShare`):
   доля точек ряда, где `|advantage| < gate`,
   `gate = (1500 / 10) * durationMinutes` (порог `intrigueGoldPer10Min = 1500`
   золота на 10 минут). Перевод в балл: линейно из `[0.1, 0.7]` → `[0, 100]`.
2. **Смены лидерства** (`leadChanges`): число смен знака преимущества.
   Балл: линейно из `[0, 8]` → `[20, 100]` (порог `minLeadChangesForComeback = 2`).
3. **Средний размер отрыва** (`meanLeadPer10Min`): среднее `|advantage|`,
   пересчитанное на 10 минут матча. Балл: линейно из `[6000, 500]` → `[0, 100]`
   (обратная шкала: меньше отрыв — выше балл).

Если доступен только один ряд (`xp_adv` без `gold_adv`) — используются
доступные ряды, покрытие отражается в списке `missing`.

### 1.2. Возможность влиять на игру (0–100)

Усреднение по доступным слагаемым:

| Слагаемая | Шкала | Примечание |
|---|---|---|
| Участие в убийствах команды `(kills+assists)/teamKills` | `[0.25, 0.55]` → `[15, 100]` | пороги `low/highKillParticipation` |
| Урон по героям в минуту | `[150, 900]` → `[20, 100]` | |
| Урон по строениям в минуту | `[20, 250]` → `[20, 100]` | |
| Лечение в минуту | `[0, 200]` → `[40, 95]` | |

Убийства сами по себе не дают балла — только в сочетании с участием, уроном и давлением.

### 1.3. Полезность союзников (0–100)

| Слагаемая | Шкала |
|---|---|
| Равномерность распределения ассистов по команде (`assistBalance = clamp(1 - deviation/(2*expected))`) | прямое значение 0–100 |
| Доля игроков команды с ненулевыми ассистами | `[0.3, 1.0]` → `[20, 100]` |
| Суммарный урон по строениям команды | `[2000, 15000]` → `[30, 100]` |
| Суммарное лечение команды | `[0, 8000]` → `[45, 90]` |

Компонент описывает **измеримые** признаки взаимодействия. Токсичность,
саботаж и мотивы игроков по KDA не определяются.

### 1.4. Темп и вовлечённость (0–100)

| Слагаемая | Шкала |
|---|---|
| Длительность в контексте Turbo (`turboDurationIdeal = [1200, 2100]` c) | 300 c → 45; 1200 c → 85; 2100 c → 90; 3600 c → 50 |
| Плотность событий `(kills+deaths)/min` | `[0.15, 1.2]` → `[25, 100]` |
| Командные бои в минуту (если `teamfights` есть) | `[0.05, 0.5]` → `[30, 100]` |

Длинный матч автоматически не считается плохим: длительность оценивается
в связке с активностью.

### Итог и правила перераспределения весов

- Доступный балл: `score = Σ(component_score × weight) / Σ(available_weights)`,
  округление до целого, ограничение `[0, 100]`.
- Недоступный компонент **исключается**, его вес делится пропорционально
  между доступными (через деление на сумму доступных весов).
- **Минимальное покрытие** `MIN_EXPERIENCE_COVERAGE = 0.5` (50% суммы весов).
  Ниже — `score = null` и текст причины (`insufficientReason`).
- `coverage` и `confidence` (`low < 0.65 ≤ medium < 0.85 ≤ high`) показываются в UI.
- В списке матчей (`src/analytics/summary-scores.ts`) считается **упрощённый
  вариант** по кратким полям истории (темп + вовлечённость, веса 0.5/0.5),
  он помечается знаком `≈` как приблизительный.

## 2. Player Performance Score («Качество вашей игры»)

Модель: `src/analytics/player-performance/index.ts`. Веса — для Turbo.

| Компонент | Вес |
|---|---:|
| Экономика и темп | 20% |
| Командные сражения | 25% |
| Цели и реализация преимущества | 20% |
| Выживаемость и решения | 15% |
| Полезность для команды | 10% |
| Эффективность предметов и сборки | 10% |

### Формулы компонентов

1. **Экономика**: усреднение GPM `[300, 700] → [10, 100]`, XPM `[300, 800] → [10, 100]`,
   нетворс относительно среднего команды `ratio ∈ [0.6, 1.3] → [20, 100]`.
2. **Командные сражения**: усреднение KDA `(K+A)/max(D,1)` `[0.5, 5] → [10, 95]`,
   участие в убийствах `[0.15, 0.65] → [15, 100]`,
   доля в уроне команды `[0.08, 0.3] → [20, 100]`. KDA — лишь одна из слагаемых.
3. **Цели**: урон по строениям `[500, 4000] → [15, 100]` и его доля в команде
   `[0.05, 0.4] → [25, 95]`.
4. **Выживаемость**: смерти в минуту (обратная шкала `0.09 → 0` → `[15, 100]`),
   доля смертей от команды `[0.35, 0.08] → [25, 95]`.
   `leaver_status > 1` жёстко снижает балл до 5.
5. **Полезность**: доля ассистов `[0.1, 0.35] → [25, 100]`,
   лечение `[0, 3000] → [45, 95]`, покупки `ward_observer` из `purchase_log`
   `[0, 6] → [40, 90]`.
6. **Предметы**: заполненность слотов `[3/6, 1] → [30, 85]`,
   стоимость сборки по `GET /constants/items` `[4000, 20000] → [25, 100]`,
   доля непотраченного золота (обратная) `[0.3, 0.02] → [30, 90]`.

### Правила при неполных данных

- Отсутствующий показатель делает компонент **недоступным** (`missing` со списком
  полей); значение не подменяется нулём.
- Веса доступных компонентов перераспределяются пропорционально.
- **Минимальное покрытие** `MIN_PERFORMANCE_COVERAGE = 0.5`; ниже — отказ
  от итогового балла с объяснением.
- Оценка **не зависит исключительно от победы**: `radiant_win` в формулу не входит.

## 3. DataCoverage

`src/analytics/dataCoverage.ts` собирает факт наличия полей
(`duration`, `players`, `player_stats`, `gold_adv`, `xp_adv`, `objectives`,
`teamfights`, `items`, `purchase_log`) и возвращает `available/missing/ratio`.
Результат показывается в карточках оценок как «Покрытие данных» и
«Нет данных: …».

## 4. Субъективное впечатление

Блок «Как тебе матч?» (`src/features/feedback/FeedbackBlock.tsx`) — четыре
шкалы 1–5, хранятся только в `localStorage` (`dota2analytics:feedback`).
Субъективная и автоматическая оценки **не объединяются** и показываются раздельно.

## 5. Ограничения

- Ответ Steam OpenID серверно не проверяется (см. README); ID используется
  только для выбора публичного профиля.
- OpenDota может отдавать неполные данные (матчи без парсинга, закрытые профили,
  лимиты 429). Интерфейс показывает это явно.
- Пороги и веса V1 не откалиброваны на размеченных данных и будут меняться.
